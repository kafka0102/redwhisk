# 0040. 文件树行内新建由受控草稿行承载，不用 react-arborist 内置编辑态

**状态**：采纳（待执行）

「代码」Activity 的文件树要支持「新建文件 / 新建文件夹」：在目标目录首行出现图标 + 输入框，输入后创建实体，空值失焦即消失。文件树用 react-arborist，它自带 create/edit 状态机（`tree.create()`、`node.isEditing`、`node.submit()`、`onCreate / onRename`），但本仓的行由自定义渲染器负责，且树数据是「后端按层拉取 + 5s 轮询 + SWR 缓存」的受控数据。

## 决定

1. 新建态由一个前端合成的**草稿行**承载：把一个带哨兵 id 的合成节点插到目标目录子节点的第 0 位，随树数据一起交给 Tree；行渲染器识别哨兵 id 后渲染「文件夹 / 文件图标 + 输入框」。数据 DTO 不变，靠 id 哨兵识别，不新增字段。
2. 不使用 react-arborist 的内置 create/edit：它插入的是只存在于库内部、不受后端数据约束的节点，下一次轮询或懒加载回流就会与真实节点错位或消失；而落盘副作用本来也必须由我们实现。
3. 提交语义归草稿行：Escape、空值失焦、空值回车 = 取消；非空失焦、非空回车 = 提交；提交失败（非法名、已存在）保持输入态并提示，便于就地改名。

## 后果

- 交给 Tree 的渲染数据中会短暂存在一个仅前端可见的哨兵节点；提交成功或无值取消后即清除，真实节点随目录刷新进入树。
- 草稿行的插入与名称校验是可纯函数化的确定性逻辑，测试无需依赖 arborist 的虚拟化。
- 后端命令与目录刷新时机（创建后立即强刷该目录）成为该能力的行为契约，而非库的默认行为。

## 考虑过的替代方案

| 方案 | 未采纳原因 |
| --- | --- |
| react-arborist 内置 `tree.create()` + `node.isEditing` | 库内节点与受控 data 构成双事实源，轮询 / 懒加载回流即错位；自定义渲染器下仍要自写输入框 |
| 居中「新建文件」对话框 | 与 VS Code 心智不一致，脱离「当前目录」的空间上下文，且与用户要求的行内形态相反 |
