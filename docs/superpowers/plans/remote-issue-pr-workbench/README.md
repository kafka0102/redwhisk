## 全局硬约束

- SQLite 是业务状态唯一事实源；远程宿主是同步来源，不是本地工作流状态源。
- 本地 `backlog / running / review / completed` 与远端 `open / closed` 是两条轴，不互相覆盖。
- 远程 Issue 正文、标题、标签和指派在 v1 只读；写回只允许创建 Issue、关闭/重开、交付摘要评论和创建 PR/MR。
- 同步或网络失败不得清空已有缓存，不得因一次 404 自动删除本地副本。
- 模式切换只改变可见性和新建默认值，不删除 Issue、评论、附件、Session、完成记录。
- 一个 Issue 可以关联多个 PR/MR，一个 PR/MR 可以关联多个 Issue。
- CLI 子进程必须走现有交互式 `PATH` 解析与 `apply_interactive_path`；不得把 token 写入命令行、SQLite 或日志。
- 跨 Tauri 边界 DTO 的 Rust camelCase 与 TypeScript 类型必须同步；新增命令、事件和错误码要同步 `tauri-contract.md`。
- 用户可见文案必须进入 i18n，所有 locale 同时补齐。
- 新增行为必须有单元或集成测试；CLI 输出使用 fixture，测试不得依赖真实网络或真实登录态。
- 不改范围外代码，不顺手重构。发现无关问题只记录，不纳入本任务。

## Agent 执行协议

每个任务文档都包含自己的边界，但所有任务共同遵守以下流程。

### 1. 开工

1. 阅读本文件、任务文档、产品设计、任务指定原型场景和根目录 `AGENTS.md`。
2. 核对任务文档「当前基线」与当前代码、前序任务完成记录。
3. 把任务文档和本文件的对应状态改为 `进行中`，记录实际开工基线。
4. 若基线已经包含任务要求，不重复实现；先补证据，再按计划校准规则处理。
5. 若发现任务边界与当前目标冲突，先写「计划校准」再编码。

### 2. 实现

1. 只实现当前任务文档列出的范围，不提前做后续任务。
2. 保留既有本地 Issue 行为；远程能力通过来源和能力判断逐步接入。
3. UI 任务必须以指定原型场景为视觉与交互基线，不允许只凭文字自由发挥。
4. 数据模型、Tauri contract、错误码、i18n 与测试随实现同步更新。

### 3. 验证

1. 先验证当前任务新增或修改的局部行为，再按 `AGENTS.md` §5 执行完整门禁。
2. UI 任务逐个对照任务文档列出的原型场景，记录差异处理结果。
3. 不允许用过滤后的测试结果冒充全量通过；过滤运行只用于定位。
4. 验证后执行 `git status --short`，确认没有格式化带出的无关改动。

### 4. 完成记录

任务只有同时满足以下条件才能标记 `已完成`：

- 代码、数据迁移、测试、i18n 和契约文档已完成。
- 任务验收项已逐条有证据。
- UI 任务已核对全部指定原型场景。
- 质量门禁已通过，或未跑项及风险已明确记录。
- 任务文档的完成记录和本文件状态表已更新。
- 当前任务相关改动已创建本地提交；未 push、未 merge、未 rebase、未 tag。

任务文档的「完成记录」至少填写：

```text
日期：
状态：已完成 / 部分完成 / 阻塞
提交：
实际改动：
验证命令与结果：
原型场景对照：
与原计划的差异：
对后续任务的影响：
未完成项及承接任务：
```

完成记录只追加，不覆盖历史。任务状态可以修改，历史记录不得重写。

### 5. 计划偏差与校准

实现与计划不完全相符时，禁止静默缩小、扩大或移动范围。按以下顺序处理：

1. 判断是否仍满足产品目标。若会偏离目标，停止并记录阻塞，不自行改需求。
2. 在当前任务「计划校准」中记录：原计划、实际情况、原因、决策。
3. 若实际实现更好且已满足验收，更新当前任务和后续任务的「当前基线」。
4. 若产生遗留项，必须指定唯一承接任务和可验收条件，不能只写“后续处理”。
5. 若前置任务吸收了后续任务能力，把后续任务改为只补缺口，并删除重复要求。
6. 若发现新依赖或依赖不再成立，更新本文件状态表和依赖图。
7. 完成以上更新后，才创建本次任务的提交。

计划校准的判断标准是最终产品目标，不是机械保留旧提示词。任何任务边界变化都必须能在本计划中找到原因、承接位置和验收证据。

## 原型验收协议

主原型文件：[issue-pr-workbench.prototype.html](../../../../src/features/issues/issue-pr-workbench.prototype.html)

原型左栏的场景编号 `s1`～`s23` 是截图和验收坐标。任务文档列出的是必须核对的场景，不是可选参考。

UI 任务执行时：

1. 在浏览器打开原型，按左栏标题定位场景编号。
2. 用户截图时建议使用 1440×900，截取完整应用外壳；至少保留左侧 Activity、surface Tab、主内容和右侧栏，不要只截一个按钮或局部卡片。
3. 截图文件名建议使用 `<任务号>-<场景号>-<主题>.png`，例如 `task-04-s18-remote-backlog.png`。
4. 实现后逐场景对照层级、密度、对齐、间距、状态、动作位置、空态和错误态。
5. 原型与设计文档语义冲突时，不自行选择；在任务文档记录冲突并暂停相关改动，等计划校准后再继续。
6. 不能把任务文档中的文字描述当作原型的替代品。文字负责边界，原型负责可见布局和交互位置。

补充原型：[completion-closeout.prototype.html](../../../../src/features/issues/issue-completion/completion-closeout.prototype.html)。任务 5、8 涉及完成弹窗时同时核对其中指定的 `s*` 场景。
