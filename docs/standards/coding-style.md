# 编码风格

## 目标

本文档定义本项目与前后端无关的通用编码风格，适用于文档、TypeScript 源码、共享包、脚本与配置代码。

当前仓库已经包含 Tauri + React + TypeScript 应用源码、Rust 核心代码、`pnpm` 脚本、Prettier、ESLint、Vitest 与 Cargo 测试。涉及 TypeScript、Rust、Prettier、lint、typecheck、test 的规则适用于当前所有开发任务。

## 命名规范

必须遵守：

- 目录、文件统一使用 `kebab-case`
- 变量、函数统一使用 `camelCase`
- 类型、接口、类统一使用 `PascalCase`
- 常量统一使用 `SCREAMING_SNAKE_CASE`
- 布尔值命名优先使用 `is`、`has`、`can`、`should` 等可判读前缀

建议：

- 名称优先表达业务语义，不为了“短”牺牲可读性
- 非通用缩写不要进入公共 API、共享类型或跨模块边界
- 同一概念在不同模块中尽量保持同名

禁止：

- 同一层级混用多套命名风格
- 用含糊缩写、序号或临时占位词作为正式命名

## 类型风格

必须遵守：

- 所有对外导出的函数、类型、配置对象和返回值必须具备明确类型
- 对外部输入优先使用 `unknown`、类型守卫或 Schema 校验，不直接扩散 `any`
- 跨模块边界的数据结构必须显式建模，不允许让调用方自行猜测

建议：

- `interface` 用于稳定对象结构
- `type` 用于联合、交叉、映射和类型组合
- 字符串枚举优先使用字面量联合，非必要不引入 `enum`

禁止：

- 以 `@ts-ignore`、`@ts-nocheck` 作为常规开发手段
- 用 `any` 作为默认逃生口并继续向外传播

## 组织方式

必须遵守：

- 一个文件应只有一个主要职责
- 同一段业务规则、转换逻辑或校验逻辑，不应在多个模块中复制分叉
- 复用抽象必须降低复杂度，而不是制造新的术语层

建议：

- 优先组合而不是滥用继承
- 先写清晰实现，稳定后再抽象
- 注释优先解释“为什么”，不是逐行复述“做了什么”

禁止：

- 把 `utils` 当作任意逻辑的垃圾桶
- 为了“未来可能会用”提前堆砌过深抽象
- 在一个文件中混合多个层次的职责

## 表单文案与视觉约束

必须遵守：

- 所有表单字段标签使用常规字重，不使用加粗强调
- 表单字段标签使用较轻的常规文本颜色，避免与正文输入值抢层级
- 字段标签负责说明，不承载额外装饰语气、营销语气或视觉强调
- 输入控件不得自动改写用户输入的大小写；共享 `Input` / `Textarea` primitive 默认必须设置 `autoCapitalize="none"`，并通过全局样式保证 `input` / `textarea` 的 `text-transform: none`
- 命令、路径、Agent 名称、标签名、搜索框等自由文本输入不得依赖局部补丁关闭自动大写；新增基础输入控件时必须在组件层统一关闭浏览器或平台的自动大小写转换

建议：

- 标签文案保持简短、事实性和可扫描
- 输入值、选择值与标签在视觉上保持明确主次，优先保证值本身可读

## 格式与提交前检查

必须遵守：

- 仓库已有 `prettier.config.mjs`，前端和配置文件格式以该配置和 `pnpm format` 覆盖范围为事实来源
- 每次完成前端代码修改后，必须先执行已配置的格式化命令，再进入 lint、typecheck、test
- Rust 代码保持 `rustfmt` 默认风格；项目当前非 fmt-clean，仅在必要时手动 `rustfmt <单文件>`，禁跑全量 `cargo fmt`（会带出大量无关漂移，且 `AGENTS.md` 质量门禁不含 `cargo fmt`）
- 执行格式化命令后，必须立即检查 `git diff --stat` 或 `git status --short`，确认格式化实际改动了哪些文件
- 若格式化命令改到了当前任务之外的文件，必须在继续验证或提交前显式处理：要么把这些文件一并纳入当前任务并说明原因，要么回退这些无关格式化改动；不得把它们留成“顺手改了但未提交”的状态
- 执行 lint、typecheck、test 或其他验证命令后，如这些命令可能触发代码生成、快照更新、缓存落盘或其他文件改写，也必须再次检查 `git status --short`，不能默认工作区仍与格式化后完全一致
- 自动提交、委托提交或借助外部 Agent 提交时，以上检查点必须被明确展开为可执行步骤或命令清单，不能只保留“自检后提交”这类笼统描述
- 提交前必须清理临时调试代码、废弃分支和无用注释

建议：

- 工具链规则尽量通过根脚本、workspace 脚本或共享配置统一暴露
- 对同类问题优先用统一规则解决，而不是局部特判

禁止：

- 通过跳过格式化、关闭类型检查或局部放宽规则来掩盖工程问题
- 把调试输出、临时兜底逻辑和试验性代码直接带入正式提交
